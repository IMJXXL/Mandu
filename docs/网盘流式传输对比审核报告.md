## 一、架构概述

### 1.1 本项目流式管线

三个网盘共享同一套流式管线，仅在认证头和直链获取上各有差异：

```
RawXxxArchiveByteSource  →  ReadAheadArchiveByteSource  →  BlockCacheArchiveByteSource
   (HTTP Range 取块)         (8MiB 顺序预读窗口)           (2MiB×32 LRU 块缓存)
```

- `RawXxxArchiveByteSource`：调用各网盘的 `RangeClient.readRange(url, offset, len)` 发 HTTP Range 请求
- `ReadAheadArchiveByteSource`：在当前读取位置前方维护 8MiB 预读窗口，减少往返
- `BlockCacheArchiveByteSource`：2MiB 块粒度，32 块 LRU 缓存，避免重复下载

该管线仅用于**压缩包内阅读**（ZIP/CBZ/CBR 等）。**文件夹阅读**走独立的 `FolderReader` 路径，不经过此管线。

### 1.2 RCH 参考项目流式管线

RCH 统一定义 `ByteSource` trait，所有源实现 `read_at(offset, buf)` 随机访问：

```
ByteSource::read_at(offset, buf)
    ├── 直链缓存（TTL + LRU）
    ├── SingleFlight（按 fid 合并并发取链请求）
    ├── HTTP Range 请求
    ├── CDN 独立限速门控（115 独有）
    └── 错误恢复（WAF 冷却 / CancelSignal / 重试）
```

RCH 的管线在 Rust 层统一处理限速、去重、重试，各源只需实现认证和直链获取逻辑。

### 1.3 本项目 WebDAV 基线

WebDAV 实现是本项目最成熟的流式阅读方案，具备以下网盘模块所没有的能力：

## 三、FolderReader 共性问题

三个网盘的文件夹阅读器（`QuarkFolderReader.kt`、`BaiduFolderReader.kt`、`FolderReader115.kt`）实现模式完全一致，存在相同的结构性缺陷：

### 3.1 整文件下载每页

**现状**：`loadPageRaw()` 对每页图片执行完整的 HTTP GET 下载，将整个文件读入 `ByteArray`：

```kotlin
// QuarkFolderReader.kt:53-57
val response = client.get(downloadInfo.url) { ... }
response.body<ByteArray>()

// BaiduFolderReader.kt:52-55
val response = client.get(downloadInfo.url) { ... }
response.body<ByteArray>()

// FolderReader115.kt:69-72
val response = client.get(downloadInfo.url) { ... }
response.body<ByteArray>()
```

**问题**：
1. **OOM 风险**：大图（>10MB 的 TIFF/无损 PNG）整文件读入内存，在低内存设备上易触发 OutOfMemoryError
2. **无预读**：每页独立下载，无顺序预读，翻页延迟高
3. **无缓存**：已下载的页面无缓存，回翻时重新下载
4. **无并行**：页面串行下载，无法利用带宽

**对比 RCH**：RCH 的文件夹阅读通过 `FolderByteSource` 实现 `ByteSource` trait，支持 Range 随机访问，可接入统一的预读和缓存管线。

### 3.2 无 Range 请求

FolderReader 完全不使用 HTTP Range，即使 CDN 支持 Range。对于大图（如 50MB 的 TIFF），无法只读取需要解码的部分。

### 3.3 OOM 处理不足

三个 FolderReader 都有 OOM 降级处理（`inSampleSize = 2`），但这是被动兜底，而非主动预防。在内存紧张时仍可能崩溃。

## 五、优化建议

### 5.1 P0 优化（建议立即处理）

#### 建议 1：FolderReader 改为 Range 流式读取

**目标**：消除 OOM 风险，接入预读缓存管线

**方案**：
1. 为 FolderReader 创建 `FolderByteSource` 实现 `ArchiveByteSource` 接口，通过 RangeClient 按 Range 读取图片数据
2. 复用 `ReadAheadArchiveByteSource` + `BlockCacheArchiveByteSource` 管线
3. `loadPageRaw()` 改为从管线读取，而非整文件下载
4. 对于不支持 Range 的 CDN，回退到整文件下载（但加 size 检查，超过阈值时用 `BitmapFactory.Options.inSampleSize` 降采样）

**工作量**：约 3-4 小时/网盘（三个网盘结构一致，可共享基类）

#### 建议 2：206 Content-Range start 校验

**目标**：防止 CDN 返回错误偏移导致数据错位

**方案**：在各 RangeClient 的 `readRange()` 方法中，206 响应时校验 `Content-Range` 的 start 与请求 offset 一致：

```kotlin
206 -> {
    val cr = response.headers["Content-Range"]
    val rangeStart = parseContentRangeStart(cr)  // 复用 WebDavClient 的解析逻辑
    if (rangeStart == null || rangeStart != offset) {
        throw RemoteRangeNotSupportedException(url, offset)
    }
    return response.body()
}
```

**工作量**：约 1 小时（三个 RangeClient 各改 5 行，解析函数从 WebDavClient 提取为共享工具）

### 5.2 P1 优化（建议近期处理）

#### 建议 3：添加传输层重试

从 `WebDavClient.kt` 提取 `withTransportRetry` 为共享工具，在各 RangeClient 的 `readRange()` 中包裹请求。重试策略：最多 3 次，指数退避（500ms / 1s / 2s），仅重试 5xx 和网络超时。

**工作量**：约 2 小时

#### 建议 4：添加 downloadGate 并发闸门

从 `WebDavClient.kt` 提取 `downloadGate` 机制为共享 Semaphore，各网盘按自身限速配置并发数（夸克 4 / 百度 3 / 115 2）。

**工作量**：约 1 小时

#### 建议 5：百度添加直链缓存

在 `BaiduBookRouter` 中添加 LRU 缓存（TTL 300s, 容量 128），缓存 dlink 结果。key 为文件路径，value 为下载 URL + 过期时间。

**工作量**：约 1 小时

#### 建议 6：百度添加 Content-Type json 拦截

在 `BaiduRangeClient.readRange()` 中，检查响应 `Content-Type`，若为 `application/json` 则解析错误码并抛出明确异常，防止错误体被当作图片数据写入缓存。

**工作量**：约 30 分钟

#### 建议 7：115 添加 WAF 405 冷却

在 `RangeClient115` 中，405 响应时进入冷却期（60s），冷却期内所有请求直接抛出 `WafCooldownException`，避免排队请求继续触发 WAF。

**工作量**：约 1 小时

#### 建议 8：115 添加 CDN 独立限速

在 `RangeClient115` 中，为 CDN 请求添加独立的 RateLimiter（4 r/s + 突发 6）和在途并发限制（2），与 API 请求的限速分离。

**工作量**：约 1 小时

### 5.3 P2 优化（建议中期处理）

#### 建议 9：提取 DiagTracer 为共享工具

从 WebDAV 实现中提取 `DiagTracer`，在各 RangeClient 中记录请求耗时、命中/未命中、重试次数等指标，输出到诊断日志。

**工作量**：约 2 小时

#### 建议 10-15：ZipAsDir / sticky session / 文件夹索引缓存 / 开书重试 / solid 回退 / 文档格式关管线

这些均为 WebDAV 已实现的成熟机制，可逐步移植。建议按使用频率排序，优先移植「开书失败自动重试」和「文档格式关管线」。

## 六、总结

### 6.1 整体评价

三个网盘的**压缩包阅读**管线（Raw → ReadAhead → BlockCache）架构合理，核心流式能力已具备。主要差距集中在**错误恢复**（重试/回退/校验）和**并发控制**（闸门/限速）两个维度，这些是 WebDAV 实现已经成熟但网盘模块尚未移植的能力。

**文件夹阅读**是当前最薄弱的环节，整文件下载模式存在 OOM 风险和无预读无缓存的性能问题，建议优先改造。

### 6.2 优先级建议

```
立即处理：建议 1（FolderReader Range 化） + 建议 2（206 校验）
近期处理：建议 3-8（重试 + 闸门 + 百度缓存 + 115 WAF/限速）
中期处理：建议 9-15（诊断 + ZipAsDir + sticky + 重试/回退）
长期规划：建议 16-20（代际失效 + 多域名 + 并行 Range + 优先级）
```

### 7.2 多设备同步

| 功能 | RCH | MangaReader |
|------|-----|-------------|
| WebDAV 同步 | ✅ | ❌ |
| 三方合并 | ✅ | ❌ |

**差距分析**：RCH 独有多设备同步功能，通过 WebDAV 实现阅读进度、书架、设置的三方合并同步。引入价值：**高**。多设备同步是重度用户的核心需求，用户在手机和平板上阅读同一本书时，进度无法同步是重大痛点。

**实现建议**：
1. 在 `Database.kt` 中增加同步状态表（记录每条记录的最后修改时间）
2. 通过 WebDAV 上传/下载增量同步包（JSON 格式）
3. 三方合并策略：以时间戳为准，冲突时保留两条记录让用户选择
4. 工作量：约 20-30 小时

### 7.3 阅读统计

| 功能 | RCH | MangaReader |
|------|-----|-------------|
| 阅读时长统计 | ✅ | ❌ |
| Top10 排行 | ✅ | ❌ |

**差距分析**：RCH 独有阅读统计功能，记录每本书的阅读时长并生成 Top10 排行。引入价值：**中等**。用户喜欢看到自己的阅读数据，实现成本低（在阅读时记录时间戳，定期聚合）。

**实现建议**：
1. 在 `Database.kt` 增加阅读会话表（bookId, startTime, endTime, pageCount）
2. 统计页面展示总时长、Top10、阅读热力图
3. 工作量：约 8-12 小时

## 八、元数据与刮削对比

### 8.1 智能刮削

| 功能 | RCH | MangaReader |
|------|-----|-------------|
| 在线元数据刮削 | ✅ | ❌ |
| E 站元数据导入 | ✅ | ❌ |
| EH 订阅 | ✅ | ❌ |

**差距分析**：RCH 独有完整的元数据刮削体系，支持从多个来源自动获取漫画标题、作者、标签等信息，并支持 E 站（E-Hentai）元数据导入和订阅。

**引入价值评估**：
- **智能刮削**：中等。用户书架中的漫画文件名往往不规范，自动刮削可以补全标题、作者、封面等信息，提升书架浏览体验。但刮削源（如 Bangumi、漫画DB）的 API 稳定性参差不齐，维护成本高。
- **E 站元数据导入**：中等偏低。仅对 E 站用户有价值，受众面窄。
- **EH 订阅**：低。需要持续维护 EH API 兼容性，且 EH 政策变动频繁。

## 十一、质量差距与改进方向

### 

RCH 的网盘模块经过长期打磨，具备完善的错误恢复和限速机制。MangaReader 的网盘模块是新建的，功能可用但健壮性不足：

| 维度 | RCH | MangaReader |
|------|-----|-------------|
| 错误恢复 | WAF 冷却 / CancelSignal / 重试 / 回退 | 基本异常捕获 |
| 限速 | CDN 独立门控 / 优先级老化 | 单一 RateLimiter |
| 诊断 | Span 追踪 / 性能计数 | Log.w 日志 |
| 缓存 | 直链缓存 + SingleFlight | 直链缓存 + SingleFlight（部分） |

**改进方向**：逐步移植 WebDAV 实现中的成熟机制（重试、闸门、诊断）到网盘模块。

### 11.3 代码质量差距

| 维度 | RCH | MangaReader |
|------|-----|-------------|
| 类型安全 | Rust 编译时保证 | Kotlin + Null safety |
| 错误处理 | Result<T, E> 类型 | try-catch + nullable |
| 并发安全 | Rust 所有权模型 | Coroutine + Mutex |
| 测试覆盖 | 有 Rust 单元测试 | 测试覆盖不足 |

**改进方向**：MangaReader 的 Kotlin 代码质量良好，但测试覆盖不足。建议增加关键路径的单元测试（网盘 API 客户端、流式管线、超分推理）。
